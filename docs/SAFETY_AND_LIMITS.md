# 安全、恢复与已知限制

## 不应误解的承诺

| 本工程提供 | 不代表 |
|---|---|
| Block JSON 快照 | 图片/附件二进制、评论、协作者、分享权限都被备份 |
| 文本回滚计划 | 删除/新建/合并/表格结构可以事务性恢复 |
| 本地目录约束 | 所有上游原生工具和整个 Node 进程都被沙箱隔离 |
| 固定源码 commit | 首次 npm 解析的所有传递依赖也已在交付包锁定 |
| 离线测试通过 | 上游已编译、SDK 已联调、账号权限已验证 |
| 单进程共享 Token | 模型从此能访问用户无权访问的文档 |
| 关闭遥测 | 文档不会上传飞书或不会发给用户使用的模型服务 |
| 本地快照预览 | 飞书操作成为了跨系统事务、失败永远能原样还原 |

## 原生修改风险

`docs__feishu_update_document` 的固定上游实现会删除旧文档再重建，不要把它当作原链接不变的 PATCH。模型默认无法直接调用；需同时允许 native writes 和 native destructive 才能进入。其他复杂 Block 工具也保留其原有行为，未被统一包装成安全计划。

新写的 FeishuApi 不自动重试写请求。文档上游环境设置 `FEISHU_MAX_RETRIES=0`，避免其通用重试配置导致重复请求；但原生复杂业务仍可能由多个 API 步骤组成，不保证原子性或 exactly-once。第三方上游原有的清理临时导入文件等行为也仍然存在。

## 导入失败的人工处理

`kb_inspect_plan({planId})` 查看：

- `job.items` 中的文件、状态、documentId、父节点、revision；
- `job.directories` 中可能成功创建但响应丢失的目录节点；
- `error` 和已完成的映射。

遇到 `needs_inspection`，同计划不再自动执行，同目的地的新导入也被阻止。不得通过改数据目录、删除计划来绕过这个保护。

核对飞书实际结果后，调用 `kb_reconcile_import`。这是**人工确认后的本地状态修复**，不修改飞书。

已实际创建但响应丢失：

```json
{
  "planId": "失败计划ID",
  "confirmed": true,
  "resolutions": [
    {"path": "AI/RAG.md", "outcome": "adopt", "document": "实际创建文档的URL或ID"}
  ]
}
```

系统会确认文档可读、处于记录的 Wiki 父节点，并拒绝接管其他文件的文档或把旧版本当成新上传。它不能自动证明渲染后的文档与本地 Markdown 完全无损相等，因此接管后仍标记为 remoteEdited。

人工确定这次没有创建文档：

```json
{
  "planId": "失败计划ID",
  "confirmed": true,
  "resolutions": [
    {"path": "AI/RAG.md", "outcome": "not_created"}
  ]
}
```

每个 `uploading/created` 项都必须有且只有一个 resolution。如果上游已经返回 documentId，不允许声明 not_created。没有 documentId 时的 not_created 依赖你的实际核对，系统无法通过“没有收到响应”证明创建未发生。

部分目录创建失败而未开始任何文档上传时，resolution 可以为空数组；仍要人工检查目录结果。后续导入会按名称重新查询目录并拒绝同名歧义。

状态修复完成后标记 `closed_after_review`，再生成新的导入计划。不会自动重放整个旧任务。

## 文本修改失败

若 API 超时、写后读取失败、返回文字不一致，计划会保留 `needs_inspection`。应先 `kb_read` 核对当前状态。文本计划没有“不看远端直接再次发送”的快捷恢复按钮。

仅 `applied` 的文本计划可通过 `kb_plan_rollback` 生成逆向计划，且远端 revision 必须等于修改完成时的版本。反向计划也要再次审批；期间出现并发修改会拒绝执行。追加段落、结构性修改不提供自动完整回滚。

## 本地数据保护

`.local/oauth` 使用上游文件存储，Token 是本地敏感数据，不是加密保险库。根数据目录尽量设为 700，新增状态文件 600；Windows 使用 ACL。不要与其他用户共享，不要提交 Git，不要将完整 `.local` 作为调试附件发送。

进程异常退出后可能留下 `.local/server.lock`。先确认文件中的 PID 对应进程已不存在，并确认没有客户端持有同一数据目录，再人工删除锁。锁不是自动超时任务，不会擅自覆盖仍在运行的进程。

默认媒体上传关闭，远程媒体下载关闭。显式启用本地媒体时会做路径检查，拒绝已检测到的目录外引用及遍历；这是输入检查，不是能覆盖所有 Markdown/HTML 扩展语法的安全解析器。原生上传工具不受同一限制。

## 范围限制

- 仅 Feishu 中国站 Docx / Wiki URL；不承诺旧版 Docs、Sheets、Base 或国际 Lark URL 的安全高层操作。原生工具按上游支持范围提供。
- Markdown 导入的复杂语法、嵌套表格、图片、公式、画板等以真实飞书 API 和上游行为为准，需要用自己的测试集验证。
- `kb_plan_append` 只追加纯文本；`kb_plan_patch` 不把 Markdown 自动转换成复杂富文本。
- 辅助 Markdown 导出可能损失结构与样式；JSON 有完整读取到的 Blocks，但不包含媒体字节和所有协作元数据。
- 缓存搜索不是语义向量检索，不主动扫描整个 Wiki，也不是索引一致性承诺。
- 没有后台持续 watcher、自动双向同步、无人值守冲突合并、分布式锁或公网多用户认证。
- 单次安全文本更新或追加最多 50 个项目；文件大小默认 10 MiB；文档快照最多 100,000 Blocks。
- Native 工具按名称采取保守的读写分类，不能证明上游每个工具都完全无副作用。保留原生写入默认关闭。

正式知识库迁移前，请用副本验证你实际采用的 Markdown、图片、表格和权限模型。
